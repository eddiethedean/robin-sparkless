# SS-20: Connect feature scope across Phases 4–10

> [Index](README.md) · [Roadmap](ROADMAP.md) · [Decisions](DECISIONS.md) · [Validation](VALIDATION.md)

## Purpose and compatibility baseline

Turn the Phase 4–10 roadmap into testable feature slices for an unmodified `pyspark-client` against the Sparkless Connect server. Spark 4.0.5 is the initial semantic reference already used by SS-09/10. Each phase freezes the client version, protocol fixtures, supported feature matrix, and known deviations before implementation. Later Apache Spark releases may add APIs; they do not silently expand this contract.

Spark's public DataFrame surface is much larger than a bounded single-node server can promise. The official [DataFrame API](https://spark.apache.org/docs/4.0.5/api/python/reference/pyspark.sql/dataframe.html), [built-in SQL functions](https://spark.apache.org/docs/4.0.5/api/sql/index.html), [SQL syntax](https://spark.apache.org/docs/4.0.5/sql-ref-syntax.html), and [Structured Streaming guide](https://spark.apache.org/docs/4.0.5/streaming/index.html) are source inventories, not an automatic implementation checklist. Prioritize common relational ETL, types, storage, and recovery. Keep distributed scheduling, RDD/SparkContext, arbitrary configuration, and unrestricted Spark compatibility out of scope.

| **9 / 4.25 — SS-18** | Optional restart recovery for named eligible operations and sessions | Persist server/session generation, operation identity, semantic/backend identity, completed outcome, response schema/data and replay cursor; recover eligible Connect sessions, reattach/replay without rerunning producers, retain release/expiry tombstones, fence prior owners. The Phase 4 DuckDB SQL list and Phase 7 Polars Connect list are intentionally not identical. An optional backend may support a capability earlier, but it must publish a backend-specific matrix; its support does not silently become default Polars support. Likewise, a Python UDF, Delta, JDBC or streaming capability remains disabled unless its package/runtime is explicitly enabled.

## Delivery order and decisions to close

1. **Before Phase 4 implementation:** D15 freezes SQL statement classes, expression operators, aggregates, joins, table commands and transactionally safe writes for DuckDB. Build a shared client corpus that exercises both `spark.sql()` and DataFrame plans and checks the same schemas/values where semantics overlap.
2. **Before Phase 5 implementation:** D12 chooses each UDF form and Jobs operation independently, including client serialization, Python/Pandas/PyArrow versions, type support and worker isolation. Do not ship a generic `udf` checkbox.
3. **Before Phase 6 implementation:** D13 enumerates Delta protocol features, UC catalog operations, credential scope and atomic write subset. Validate with independent Delta readers and catalog clients.
4. **Before Phase 7 implementation:** D16 turns the proposed operator/function list into a machine-readable capability registry, with arity, accepted types, null/NaN/ANSI behavior, output schema, backend, and negative fixtures. Prioritize the relational core before rare functions.
5. **Before Phase 8 implementation:** D17 freezes connector options, path/credential policy, schema inference, write modes, partition behavior, artifact limits and cache/checkpoint lifetimes per connector.
6. **Before Phase 9 implementation:** D18 maps durable identity and commit receipts across each backend and every enabled mutation; publish an eligibility table by operation and storage owner.
7. **Before Phase 10 implementation:** D19 freezes source/sink/operator combinations as a matrix, not independent feature lists. Prove source offsets, state snapshots and sink batch commits recover together.

For every phase, the acceptance corpus must include representative pipelines, empty inputs, nulls, duplicate labels/rows, boundary and overflow values, unsupported descendant rejection before effects, session isolation, cancellation, replay, and resource limits. A successful happy-path example cannot enable neighboring operators or types.

## Compatibility-package completion milestone

After Phases 3–10 finish their resolved matrices, [SS-21](21-versioned-connect-packages.md) certifies the complete planned 4.0 server baseline and publishes `sparkless-connect40` in Phase 11 / 4.27. Separate Phases 12–14 then target `sparkless-connect35`, `sparkless-connect41` and `sparkless-connect42`, with a server feature/semantic audit for each version. The early Phase 3 SparklessConnect helper remains independently useful; it does not imply certification of the completed server baseline.
