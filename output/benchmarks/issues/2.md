# perf(engine): preserve exact range-count fast paths for dynamic integer literals

## Problem and evidence
`spark.range(n).filter("id > 5").count()` increases with input size: 18.79 ms at 1M rows and 47.31–48.62 ms at 10M rows in previous benchmark variants; local Spark's 10M filtered count was ~29.6 ms. A follow-up run measured 19.51 ms at 1M and 50.78 ms at 10M (three warm observations). Exact assertions return n-6.

## Likely cause from source inspection
The existing arithmetic shortcut appears to miss the normal core-IR integer path:
- [expr_ir.rs](https://github.com/eddiethedean/robin-sparkless/blob/v4.18.0/crates/robin-sparkless-polars/src/expr_ir.rs): `lit_from_core` maps I64 to `lit(*n)`.
- Pinned Polars 0.53.0's `make_dyn_lit!(i64, Int)` produces `LiteralValue::Dyn(DynLiteralValue::Int(...))`.
- [dataframe/mod.rs](https://github.com/eddiethedean/robin-sparkless/blob/v4.18.0/crates/robin-sparkless-polars/src/dataframe/mod.rs): `integer_literal` accepts only `LiteralValue::Scalar`.
- `RangeCardinality::count_matching` therefore cannot extract this threshold; `filter` cannot populate its exact `row_count_hint`.
- `count_with_cancellation` falls back to `count_range_batches`, materializing and filtering 16,384-row source chunks.

This is a source-supported hypothesis, not yet confirmed with a patched binary. The shortcut already exists; repair its eligibility rather than introduce a second independent implementation.

## Suggested improvement
1. Add a regression covering the full core-IR → backend filter → cancellable count path, asserting fast-path selection for dynamic and typed integers.
2. Safely normalize/recognize dynamic integral literals in `integer_literal` with checked range conversion. Avoid changing general literal coercion semantics merely to optimize counts.
3. Retain fallback for non-integral/out-of-range literals and unsupported predicates. Preserve errors, overflow checks and cancellation checks even when no rows are materialized.
4. Separately explore safe interval propagation through simple filters, renames and limits; preserve operator order. Treat arithmetic projection overflow/coercion and compound predicates conservatively.
5. For plans that must scan, profile per-chunk plan construction and consider fusing supported operations once per batch.

## Acceptance
- Correctness against Spark for positive/negative steps, empty ranges, strict/inclusive thresholds, reversed comparisons and integer boundaries; test both Connect string '>' and Column '>=' predicates.
- The eligible exact range-count path must avoid row materialization, with near-flat end-to-end latency across 1k/1M/10M rows (allow fixed RPC noise).
- Initial performance target: ≥2× faster 10M filtered count than the same-machine released baseline.
- Do not generalize count metadata to collection: predicates and output values must still execute correctly.
- Meet the shared small-job guardrails below.

## Measurement context and small-job guardrails
Measured 2026-10-31 on Apple M4 Pro (12 logical CPUs, 24 GiB), Python 3.11.15, Sparkless API 4.18.1 / native and server 4.18.0, pyspark-client 4.0.5, local Spark 4.0.5 with Java 17. Native Polars/Rayon/OpenMP pools limited to four threads; local Spark uses local[4]. Published packages, no implementation changes. Baseline workload medians pool 24 timed actions across three fresh runtimes; engines run sequentially in rotating order.

Preserve current small-job performance with paired baseline/candidate runs on the same machine: three fresh runtimes, at least 20 measured iterations after warmup, identical correct outputs. Gate median regressions above max(5%, 1 ms) and p95 regressions above max(10%, 2 ms), subject to repeatable evidence rather than one noisy sample. Include 10/100/1,000/10,000-row Python-tuple ingestion+filter+count (currently ~16–19 ms), 25-row preview (~15.7 ms), nullable/mixed-type cases, schema analysis, startup and the session-fixture pytest suite. Compare RSS, CPU, first-batch latency and cancellation latency as well as wall time. These are proposed acceptance thresholds, not achieved improvements.
