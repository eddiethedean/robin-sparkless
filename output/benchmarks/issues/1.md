# perf(connect): vectorize bounded Arrow export instead of assembling one-row frames

## Problem and evidence
Large range results scale poorly despite bounded Arrow transport:

| Workload | Sparkless Connect | Local Spark |
|---|---:|---:|
| range(10_000).select("id").collect() | 112.25 ms | 16.64 ms |
| range(100_000).select("id").collect() | 1,030.93 ms | 97.23 ms |
| range(1_000).filter("id > 1000").collect() | 42.21 ms | 11.89 ms |

A follow-up split of the Connect path measured ~881.7 ms to obtain the Arrow table for 100,000 rows, versus ~97.6 ms to convert that table to Python Rows (medians of three warm observations after one warmup). A separate cProfile run spent ~0.893 s waiting in the gRPC iterator; client Arrow-to-Row conversion took ~0.174 s under profiler overhead. This localizes most elapsed time upstream of Python row conversion; it is not a native CPU profile or proof that all waiting is server compute. Empty-result collection grew from ~47.1 ms for 1,000 input rows to ~330.4 ms for 10,000.

## Source evidence
In [dataframe/mod.rs at v4.18.0](https://github.com/eddiethedean/robin-sparkless/blob/v4.18.0/crates/robin-sparkless-polars/src/dataframe/mod.rs):
- `to_arrow_ipc_batches_internal` constructs the range producer with source chunk size **1**, or uses `collect_batches(1)` for lazy sources.
- `next_source_row` slices a single-row frame; `PolarsIpcBatchIterator::next` accumulates these frames.
- `combine_rows` repeatedly calls `vstack_mut`; `serialize_batch` then rechunks.
- `RangeBatchProducer::next_batch` applies filter/project operations per source chunk, including native plan collection.

This is a strong candidate for the linear per-row overhead and repeated work on empty predicates. The one-row policy explicitly protects in-flight byte budgets, so simply increasing the chunk constant is insufficient.

## Suggested improvement
1. Keep data columnar: consume bounded frame/Arrow slices, concatenate chunks only when necessary, and serialize directly without a one-row-frame round trip.
2. Choose source chunk sizes using a conservative byte budget and schema widths; retain a minimal fast path for tiny results. Use conservative fallback for variable-width/nested data and oversized single cells.
3. Split output slices against actual serialized size, preserving independent IPC decoding and schema fidelity. Avoid serializing the full same batch repeatedly when splitting.
4. Preserve early LIMIT termination and schema-bearing empty batches. Instrument source rows/chunks, native executions, allocation/rechunk time and serialization time to verify the mechanism.
5. Keep response/result/replay caps, error-before-truncation, offsets, metadata/nullability, duplicate labels, cancellation, slow-reader backpressure and bounded RSS intact.

## Acceptance
- Demonstrate at least 2× improvement for the 100k-row range collection against the released baseline on the same machine (initial target, not a promised result).
- Also benchmark 1k/10k/100k results, empty filters with 1k/10k inputs, wide columns and variable-length strings; record first-batch and total latency.
- No row-sized native execution per source row on the optimized path; memory remains explicitly bounded independently of total input.
- Meet the shared small-job guardrails below.
- Related #1584 addresses the public chunked-collection API; this issue targets the existing server IPC exporter implementation.

## Measurement context and small-job guardrails
Measured 2026-10-31 on Apple M4 Pro (12 logical CPUs, 24 GiB), Python 3.11.15, Sparkless API 4.18.1 / native and server 4.18.0, pyspark-client 4.0.5, local Spark 4.0.5 with Java 17. Native Polars/Rayon/OpenMP pools limited to four threads; local Spark uses local[4]. Published packages, no implementation changes. Baseline workload medians pool 24 timed actions across three fresh runtimes; engines run sequentially in rotating order.

Preserve current small-job performance with paired baseline/candidate runs on the same machine: three fresh runtimes, at least 20 measured iterations after warmup, identical correct outputs. Gate median regressions above max(5%, 1 ms) and p95 regressions above max(10%, 2 ms), subject to repeatable evidence rather than one noisy sample. Include 10/100/1,000/10,000-row Python-tuple ingestion+filter+count (currently ~16–19 ms), 25-row preview (~15.7 ms), nullable/mixed-type cases, schema analysis, startup and the session-fixture pytest suite. Compare RSS, CPU, first-batch latency and cancellation latency as well as wall time. These are proposed acceptance thresholds, not achieved improvements.
