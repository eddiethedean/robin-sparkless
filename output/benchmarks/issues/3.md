# perf(connect): improve mixed-job scheduling and backpressure without regressing small-query latency

## Problem and evidence
Larger operations can occupy the same admission resources as short tests. Raising admission alone improves some throughput but does not establish fairness or memory safety.

Mixed workload (each client: ingest/filter/count 1k orders, nullable-order collection, preview 25 rows, collect 10k rows), nine rounds per client count across three fresh runtimes:

| Concurrent sessions | Default active=2 | Active=4 | Local Spark local[4] |
|---|---:|---:|---:|
| 1 | 24.3 jobs/s | 23.7 jobs/s | 24.2 jobs/s |
| 4 | 38.1 jobs/s | 46.9 jobs/s | 36.0 jobs/s |
| 8 | 41.2 jobs/s | 52.6 jobs/s | 36.6 jobs/s |

These are independent sessions in Python threads. Actual pytest-xdist was also measured separately: a 38-test suite with four worker processes sharing the default server completed in 3.04 s versus 6.60 s with one local[1] Spark JVM per worker. Preserve this practical advantage.

## Source observations (hypotheses to instrument)
In [connect.rs](https://github.com/eddiethedean/robin-sparkless/blob/v4.18.0/crates/sparkless-server/src/connect.rs):
- The producer retains compute and session-compute permits across Arrow generation and response sending.
- The execution response channel has capacity one.
- `ConnectResponseSender::send` retries a full channel with a blocking sleep of up to 10 ms.
- Response data are cloned for retained replay, adding potential copying pressure.

The source shows possible scheduling/streaming coupling. The measurements do **not** quantify how much time is spent sleeping or prove that changing channel capacity will fix throughput.

## Suggested improvement
1. Add low-overhead phase measurements: admission wait, planning/compute, Arrow encoding, replay reservation/copy and blocked-send time; record per-job short-query p50/p95/p99.
2. Replace periodic full-channel polling with deadline/cancellation-aware notification or reservation, preserving wakeups and terminal-error delivery.
3. Explore separate bounded budgets for compute and live/retained response bytes. Release/yield compute capacity only when actual computation has stopped; a paused producer must not resume compute outside admission.
4. Explore fair per-session scheduling or bounded work quanta so long scans/slow readers cannot monopolize short-job capacity. Preserve session serialization and operation identity guarantees.
5. Evaluate active=2/4/8 under measured CPU and memory limits. Provide configuration guidance; do not blindly raise defaults or queue/replay limits.
6. Consider shared immutable response buffers where compatible with protobuf and replay ownership; measure before changing representation.

## Acceptance
- Benchmark sustained mixed loads at 1/4/8/16 clients with many small jobs plus a minority of large counts/collections and deliberately slow readers. Existing short runs are not capacity certification.
- Report throughput, short-job median/p95/p99, first-batch latency, CPU, RSS, queue/rejection rates and cancellation latency for baseline and candidate.
- Demonstrate a repeatable mixed-load improvement without regressing short-job latency; use the shared guardrails under matched contention as well as no contention.
- Keep bounded queues, result/replay byte accounting, deadlines, cancellation, reattach/release behavior and disconnect recovery correct.
- Retain session-fixture and four-worker pytest performance. Four-worker local baseline uses one local[1] JVM per worker, not a shared Spark Connect service.

## Measurement context and small-job guardrails
Measured 2026-10-31 on Apple M4 Pro (12 logical CPUs, 24 GiB), Python 3.11.15, Sparkless API 4.18.1 / native and server 4.18.0, pyspark-client 4.0.5, local Spark 4.0.5 with Java 17. Native Polars/Rayon/OpenMP pools limited to four threads; local Spark uses local[4]. Published packages, no implementation changes. Baseline workload medians pool 24 timed actions across three fresh runtimes; engines run sequentially in rotating order.

Preserve current small-job performance with paired baseline/candidate runs on the same machine: three fresh runtimes, at least 20 measured iterations after warmup, identical correct outputs. Gate median regressions above max(5%, 1 ms) and p95 regressions above max(10%, 2 ms), subject to repeatable evidence rather than one noisy sample. Include 10/100/1,000/10,000-row Python-tuple ingestion+filter+count (currently ~16–19 ms), 25-row preview (~15.7 ms), nullable/mixed-type cases, schema analysis, startup and the session-fixture pytest suite. Compare RSS, CPU, first-batch latency and cancellation latency as well as wall time. These are proposed acceptance thresholds, not achieved improvements.
